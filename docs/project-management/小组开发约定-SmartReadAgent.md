# SmartRead Agent 小组开发约定

## 1. 项目基本信息

- 项目名称：SmartRead Agent：AI 智读助手。
- 项目类型：Android/Kotlin 移动端 AI 阅读助手。
- 小组规模：双人小组。
- 服务课程：《软件开发实践（三）》和《软件项目管理》。
- 当前阶段：v0.1 项目立项与管理证据链初始化。

## 2. 成员分工

- 林立洲：项目负责人，负责 Android 核心开发、AI 功能设计、LiteRT 模型集成、版本管理、文档整理和提交材料收口。
- 江轩宇：参与需求反馈、安卓真机体验测试、UI 使用建议、文档校对和演示录屏配合。

说明：本项目不把两名成员写成平均承担核心开发，最终报告按真实参与情况补充姓名和具体工作。

## 3. 工程目录结构约定

- `android/`：Android/Kotlin 工程。
- `model/`：模型训练、数据和导出文件。
- `docs/`：需求、技术方案、阶段计划、演示和课程文档。
- `docs/project-management/`：项目管理过程材料。
- `screenshots/`：App、模型、仓库和项目管理截图。
- `demo/`：演示视频或素材。
- `release/`：APK、发布说明和最终版本材料。

## 4. 文件命名规则

- 文档文件使用清晰中文名称，例如 `需求说明.md`、`技术方案.md`。
- 截图文件包含页面或材料名称和日期，例如 `首页_20260620.jpg`。
- 不使用含义不清的文件名，例如 `1.jpg`、`新建文档.md`。
- 后续涉及姓名、学号的文件由本人手动改成真实信息。

## 5. Git 提交规范

提交说明使用简短中文，前缀约定如下：

- `docs:` 文档更新。
- `feat:` 新功能。
- `fix:` 修复问题。
- `test:` 测试相关。
- `chore:` 项目配置。
- `release:` 版本发布。

示例：

- `docs: 初始化项目说明文档`
- `feat: 完成文本导入页面`
- `feat: 增加本地摘要功能`
- `fix: 修复长文本输入卡顿问题`
- `test: 增加摘要功能测试记录`
- `release: 发布 v1.0 演示版本`

## 6. 分支管理规则

- `main`：稳定版本。
- `dev`：日常开发。
- `feature/summary`：摘要功能。
- `feature/agent-chat`：Agent 问答。
- `feature/litert-model`：LiteRT 模型。
- `feature/history`：历史记录。
- `docs/project-management`：项目管理文档。

日常开发先在 `dev` 或功能分支完成，测试通过后再合并到 `main`。

## 7. 沟通机制

- 主要通过 QQ 群进行沟通。
- 重要决策需要用文字记录，并保存截图。
- 线上讨论或线下讨论后，应在沟通记录索引中补充日期、主题、结论和截图文件名。
- 禁止补造不存在的聊天记录。

## 8. 任务管理机制

- 使用在线项目管理平台记录任务。
- 看板列建议为：待规划、待开发、开发中、待测试、Bug修复、已完成。
- 任务应包含负责人、优先级、状态、计划时间和说明。
- 任务状态变化应尽量截图保存，用于课程项目管理材料。

## 9. 测试验证机制

- 林立洲完成主要功能后进行自测。
- 江轩宇负责从使用者角度进行安卓真机体验测试。
- 测试范围包括文本输入、示例文本、摘要、关键词、Agent 问答、历史记录、APK 安装和真机体验。
- 测试结果必须基于真实运行情况填写。

## 10. Bug 反馈与修复流程

- 发现问题后记录 Bug 编号、日期、发现人、问题描述、严重程度和状态。
- 项目负责人确认问题后安排修复。
- 修复后补充修复说明，并由测试与反馈成员复测。
- Bug 记录只按真实测试结果填写；V1.0 已完成模拟器回归和安卓真机体验反馈，后续问题按截图或测试记录补充。

## 11. 文档维护规范

- 每个阶段结束后更新 README、阶段计划、测试记录和截图说明。
- 重要截图保存到对应目录，不混放。
- 文档中无法确认的内容统一标明真实状态，避免编造通过结论。
- 不夸大项目规模和成员贡献。

## 12. 版本发布规则

- v0.1：项目立项与资料初始化。
- v0.2：文本导入与摘要 MVP。
- v0.3：Agent 问答与知识卡片。
- v0.4：LiteRT 端侧模型集成。
- v0.5：历史记录与体验优化。
- v1.0：期末演示稳定版。

每次发布应保留提交记录、标签、发行版截图和版本说明。
